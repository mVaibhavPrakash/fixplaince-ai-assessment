# Overall Analysis

This application is built on several assumptions:

- Database tables are recreated every time the application starts. Since the database runs locally, this resets any changes made outside the application.
- Authentication is not implemented. User IDs and organization IDs are passed in request headers; no JWT is used. However, this information is not treated as the source of truth. Each request must validate the user’s information against the database.
- No GraphQL mutations are implemented, but the code is designed so that adding them later should not require extensive changes.
- Live pagination is implemented instead of maintaining a snapshot across pagination requests. I chose this approach for performance, while accepting that changing data can cause duplicate results. The frontend filters duplicates by `task.id` and uses it as the React key.

I manually created the initial configuration files, including `package.json`, Vite, TypeScript, Prettier, and ESLint configurations, for both the backend and frontend. I generally do not rely on AI for these decisions because they depend on developer preferences. I also created the initial GraphQL and database schemas manually before asking AI to improve them.

After these steps, I relied mostly on AI for implementation. I used `AGENTS.md` to guide it, documenting the project structure, implementation approach, and references to individual plan files. I prefer breaking work into smaller tasks and completing them incrementally. I also maintained `HANDOFF.md` to track the current status and preserve continuity when a session’s context limit was reached.

After each task, I manually reviewed the code. I made several changes myself and sometimes asked AI to refactor those changes or fix bugs.

## Task 1.1

During the GraphQL and database schema design, AI overlooked several issues that I identified and asked it to address:

- **Concurrency:** The initial schema lacked version fields for optimistic concurrency control. Concurrent updates could therefore overwrite each other. Versioning was added so that, when two updates use the same version, only the first succeeds and the second receives a conflict.
- **Tenant isolation:** Isolation was initially incomplete. Row-level security (RLS) was added to enforce organization-level access in database queries.
- **Indexes:** AI raised concerns about the performance cost of multiple indexes. I challenged whether approximately seven indexes justified that concern without evidence. My preference was to retain useful indexes and revisit them if future measurements showed a problem.
- **Task ordering:** AI suggested integer positions. I requested string-based positioning, using an approach such as LexoRank, to support inserting tasks between existing tasks without renumbering the entire list.
- **User lifecycle:** Rather than deleting users, the model marks them as inactive. This preserves references in comments and activity history and allows users to be reactivated later.

## Task 2.1

The backend implementation followed these decisions:

- Authentication remains outside the assessment’s scope, as explained above.
- Request inputs are validated before database operations; identity and membership are validated against the database.
- RLS enforces tenant isolation.
- Configuration and database initialization happen during server startup.
- Singleton initialization prevents unnecessary reinitialization.
- A test-driven approach was used, covering both successful operations and failure cases.

## Task 2.2

The frontend implementation followed these decisions:

- The frontend is read-only; no mutation functionality is implemented.
- The design is minimal, with filtering supported on the Kanban board.
- `App.tsx` composes the application’s main UI.
- React’s Context API handles state management without an external state management library.
- State responsibilities are divided among smaller contexts rather than one large context.
- Reusable components keep responsibilities separate and reduce duplicated code.

## Major Findings

Despite instructions to keep the code modular and maintainable, AI initially produced overly large components and state structures in both the frontend and backend. These required manual review and further refactoring.

AI also missed aspects of data integrity, consistency, and concurrency despite their inclusion in the requirements and plans. Without manual checks, these omissions could easily have remained unnoticed.

All these information can be find in the `ai-session.md` as well.

I also removed obsolete and duplicate tests generated by AI.
